# Бенчмарк DHOLE и сравнение с AutoESDCas

Все команды выполняются из корня проекта в Linux/WSL после `bash install.sh`.
Python-скрипт использует только стандартную библиотеку. R-скрипты используют
базовый R и зависимости DHOLE; для расчёта Tm нужен `primer3/src/oligotm`,
который собирается вместе с Primer3 установщиком проекта.

## 1. Повторные запуски DHOLE

```bash
bash tools/run-r benchmark/run_dhole.R
bash tools/run-r benchmark/run_dhole.R 10 10 42 local/runs/mg1655-benchmark
```

Позиционные аргументы: `N1=10`, `N2=10`, `seed=1`, необязательный новый каталог
результатов. Без последнего аргумента создаётся уникальный каталог
`local/runs/benchmark/results-ДАТА-ВРЕМЯ-PID/`. Существующий каталог не перезаписывается.

Из `local/data/MG1655.gff` один раз выбираются N2 разных CDS без возвращения.
Один и тот же набор повторяется N1 раз. Выборка использует фиксированный RNG R
и seed; CDS идентифицируются по `locus_tag`, а при его отсутствии — по `gene`.
Повторяющиеся locus tag составных/альтернативных CDS считаются одним геном.
Координаты и размер гена определяются тем же правилом, что в DHOLE: первая запись
аннотации с этим locus tag, иначе с именем gene. В NCBI GFF это обычно запись
`gene`; для составного CDS размер означает длину её интервала, а не сумму частей.
Геном берётся из `local/data/MG1655.fna`. Эти файлы скачивает `install.sh`.

Каждый ген запускается в отдельном свежем процессе DHOLE, последовательно:
всего N1×N2 процессов. Seed задаётся и внутри каждого процесса. Это **полное
время процесса**, включая загрузку R, подготовку индексов, дизайн и запись
результатов; оно не равно времени обработки гена внутри одного пакетного запуска.
Сумма времени процессов по повтору записывается отдельно. Параметры дизайна
соответствуют стандартным параметрам DHOLE, включая `--filtering-level 2`.
Системные кэши не сбрасываются.

По умолчанию используется синтетический pTarget с кассетой из интеграционного
теста проекта; pCas не добавляется. Для сравнения с реальной постановкой задайте
те же плазмиды, которые используются в AutoESDCas:

```bash
export DHOLE_TARGET_PLASMID=/absolute/path/pTarget.fasta
export DHOLE_CAS_PLASMID=/absolute/path/pCas.fasta  # необязательно
bash tools/run-r benchmark/run_dhole.R 10 10 42 local/runs/mg1655-real
```

Основные результаты:

| Файл | Содержимое |
|---|---|
| `sampled_cds.csv` | Выбранные CDS, координаты, цепь и размер гена |
| `timings.csv` | Каждая попытка: время в секундах, exit code, статус, причина ошибки, `gene_nt`, `deleted_nt`, координаты делеции |
| `run_timings.csv` | Сумма времени процессов и число успешных генов по повтору |
| `metadata.txt` | Seed, N1/N2, хеши входов, окружение R |
| `raw/run_NNN_gene_NNNN/` | Все исходные результаты DHOLE, аргументы команды, `console.log` |

`timings.csv` дописывается сразу после каждого процесса. Неуспешные попытки
остаются в таблице, размеры делеции для них пустые; они не заменяются другими
генами. Нулевой exit code DHOLE сам по себе не означает успех: проверяется
`status=ok` в `design_summary.tsv`. Если процесс бенчмарка прерван, записи уже
завершённых попыток сохраняются. Автоматического возобновления нет.

`deleted_nt` — исходная длина удаляемого интервала, **до** вставки bridge;
`gene_nt` — длина выбранной записи гена, обе длины в нуклеотидах, координаты 1-based inclusive.

## 2. Два входных CSV для AutoESDCas

```bash
python3 benchmark/export_autoesdcas.py local/runs/mg1655-benchmark
```

Получаются `autoesdcas/deletion.csv`, `autoesdcas/bridge.csv` и
`autoesdcas/manifest.csv` внутри каталога бенчмарка:

- `deletion.csv`: удаление всего **найденного DHOLE интервала**, без вставки;
  `Inserted sequence=-`, `Manipulation type=deletion`. Это не обязательно весь CDS.
- `bridge.csv`: замена того же интервала на реально использованный DHOLE bridge;
  `Manipulation type=substitution`. Учитываются укорочение bridge по фазе и
  reverse complement для CDS на минус-цепи.
- `manifest.csv`: связь уникального `Name` с повтором, геном, исходными результатами,
  координатами и вариантом. Повторы сохраняются отдельными заданиями.

CSV соответствует [официальному примеру AutoESDCas](https://github.com/tibbdc/AutoESDCas/blob/main/data_preprocessing/input/designing_both_sgRNA_and_primers_1.csv):

```text
Name,Sequence upstream of the manipulation site (>100bp),Reference sequence,Inserted sequence,Manipulation type
```

Все последовательности экспортируются в ориентации референсного FASTA.
Перед экспортом проверяются длины, границы и совпадение полной модели
отредактированного генома. Upstream по умолчанию 200 нт; требуется уникальное
точное совпадение с геномом с учётом обеих цепей. При неоднозначности увеличьте
`--upstream`; при нехватке места до начала генома скрипт выдаст ошибку.
Ошибки дизайна пропускаются с сообщением, повреждённый успешный результат
останавливает экспорт. Проверка всех данных предшествует записи файлов.

Необязательные параметры: `--genome PATH`, `--upstream 300`, `--output NEW_DIR`.
При нестандартном `--output` перенесите `manifest.csv` в `RESULTS/autoesdcas/`
перед запуском третьего скрипта. Для проверки идентичности FASTA manifest
содержит MD5 исходного файла.

Загрузите каждый вариант в AutoESDCas с тем же MG1655 FASTA. Выберите режим,
который проектирует **PCR-праймеры UHA/DHA**: режим синтеза плазмиды может не
содержать этих праймеров. Согласуйте плазмиды, длины плеч и ограничения дизайна.
Скрипты не отправляют данные на сайт и не запускают AutoESDCas автоматически.

## 3. Tm отдельных праймеров и ΔTm пары

Из `Design_result.xlsx` каждого варианта сохраните листы `Primer_UHA` и
`Primer_DHA` как CSV UTF-8 с запятыми, сохранив исходные заголовки и идентификаторы:

```text
local/runs/auto-results/
  deletion/Primer_UHA.csv
  deletion/Primer_DHA.csv
  bridge/Primer_UHA.csv
  bridge/Primer_DHA.csv
```

Поддерживаются заголовки `ID,PRIMER_LEFT_WHOLE_SEQUENCE,PRIMER_RIGHT_WHOLE_SEQUENCE`
и `Region,primer_f_seq_(5'-3'),primer_r_seq_(5'-3')` из
[исходного кода AutoESDCas](https://github.com/tibbdc/AutoESDCas/blob/main/edit_sequence_design/module/product_and_decorate_editingSeq.py).
Дополнительные столбцы игнорируются. ID имеет вид `Name;contig:start-end`, где
AutoESDCas использует 0-based half-open координаты. Они сверяются с manifest.
Если для плеча нет успешных дизайнов, сохраните CSV только с заголовком.
Не заменяйте его листом из `Failed_task.xlsx`.

```bash
bash tools/run-r benchmark/compare_primers.R \
  local/runs/mg1655-benchmark local/runs/auto-results
```

Полная форма: `RESULTS AUTO_RESULTS [OUTPUT] [GENOME] [OLIGOTM]`.
По умолчанию: `OUTPUT=RESULTS/comparison`, геном — `local/data/MG1655.fna`,
расчётчик — `primer3/src/oligotm`. Новый каталог результатов обязателен.

У DHOLE берутся выбранные финальные праймеры из WetLab, а не все кандидаты
Primer3. UHA — плечо перед делецией в референсе, DHA — после неё. Для гена на
минус-цепи переставляются и плечи, и направления F/R: `RR, RF, LR, LF`.

Для AutoESDCas связывающийся участок — самый длинный точный 3′-суффикс праймера,
однозначно совпадающий с соответствующим флангом исходного генома в нужной
ориентации, минимум 15 нт. Служебный хвост отбрасывается. Совпадающие с матрицей
основания хвоста включаются в расчёт; это определение физически связывающегося
участка, не восстановление внутренней аннотации Primer3. Несовпадения и
неоднозначное связывание отмечаются в результатах, без подстановки Tm полного
олигонуклеотида. Поэтому некоторые AutoESDCas дизайны могут не попасть в сравнение.

Для обоих инструментов Tm пересчитывается через `oligotm -tp 1 -sc 1`.
Параметры буфера берутся из `primer3_buffer_parameters()` основного проекта:
50 мМ моновалентных солей, 1.5 мМ Mg²⁺, 0.6 мМ dNTP, 50 нМ DNA.
Исходный округлённый Tm DHOLE сохранён отдельным столбцом; для сравнения
используется пересчитанный Tm. Исходные Tm AutoESDCas не смешиваются с ним.

| Выход | Что сравнивается |
|---|---|
| `primer_comparison.csv` | Tm четырёх праймеров каждого задания, последовательности, разница AutoESDCas − DHOLE, статус сопоставления |
| `pair_comparison.csv` | `abs(Tm_F − Tm_R)` отдельно для UHA и DHA одного гена/попытки; разница ΔTm между инструментами |
| `summary.csv` | Число ожидаемых и сопоставленных пар, средние ΔTm по варианту и плечу **на одних и тех же сопоставленных парах** |
| `methods.txt` | Параметры расчёта и определение метрик |

Пропущенные дизайны AutoESDCas остаются в отчёте с пустыми Tm. Неизвестные ID,
дубликаты и несовпадение координат — ошибки. Повторные запуски одного гена
сохраняются; это технические повторы, не независимые биологические наблюдения.
Скрипт не делает статистических выводов о превосходстве одного инструмента.

## Проверки без полного бенчмарка

```bash
python3 test/test_benchmark_export.py
bash tools/run-r test/test_benchmark.R
```

Тесты проверяют обе цепи, ориентацию bridge, границы, повреждённые модели,
неуспешные процессы, фиксированную выборку, повторные задания, отсутствие
результата AutoESDCas, связывающиеся участки, перестановку праймеров и ΔTm.
Тест процесса использует явно синтетическую замену DHOLE. Проверка Tm вызывает
настоящий `oligotm`; путь можно задать через `DHOLE_TEST_OLIGOTM`.
Если бинарника нет, эта часть теста явно помечается `SKIP`.
